# How to run Claude Code in loops

Loops let Claude repeat cycles of work until a stop condition is met. The four
types differ in **what you hand over**: the check, the stop condition, the
trigger, or the whole prompt. This guide maps each type to the assets this
template ships.

## Choose your loop

| Type | You hand over | Trigger | Stops when | Template asset |
|------|---------------|---------|------------|----------------|
| Turn-based | the check | your prompt | Claude judges it's done | `/verify` skill (self-verification with evidence) |
| Goal-based | the stop condition | your prompt | goal met OR try cap hit | per-wave **Goal command** in `docs/plan/implementation-waves.md` (generated by `/waves`) |
| Time-based | the trigger | an interval | you cancel, or the work concludes | `/babysit-pr` skill under `/loop` |
| Proactive | the whole prompt | schedule/event, no human | each task exits on its goal; routine runs until disabled | composition recipe below + `task-completed.sh` gate |

Rule of thumb: "Can I write the check?" → turn-based. "Can I describe done?"
→ goal-based. "Does the work arrive on a rhythm?" → time-based. "All of the
above, recurring?" → proactive.

## Recipe: verify instead of eyeballing (turn-based)

1. After any non-trivial change, invoke `/verify` (Claude also invokes it on
   its own before reporting work done).
2. It runs the gates from `CLAUDE.md → ## Commands` and exercises the changed
   behavior with tools — evidence, not opinion.
3. If your manual review still catches something `/verify` missed, encode that
   check into `.claude/skills/verify/SKILL.md` so every future loop has it.
   Fix the production line, not the part.

## Recipe: run a wave as a goal loop (goal-based)

1. Derive the plan with `/waves` — each wave ships a ready-made Goal command.
2. Invoke it, e.g.:
   `/goal wave 2 acceptance criteria pass (test + lint commands exit green), stop after 5 tries`
3. The evaluator sends Claude back until the criteria hold or the cap is hit.
   Both halves are mandatory: a **verifiable condition** (command exits green,
   score threshold, count) and a **cap**. Vague criteria break the evaluator;
   a missing cap burns tokens on an impossible target.
4. Close the wave with `/verify` before marking it ✅.

## Recipe: babysit a PR (time-based)

1. Open the PR (draft first, per the git workflow).
2. Run: `/loop 5m /babysit-pr <pr-number>`
3. Each tick, the skill checks for NEW review comments / CI failures and acts
   only when something changed — idle ticks cost one line.
4. When the PR is merged or closed, it reports and asks you to cancel the loop.

`/loop` lives in your session — laptop closed, loop stopped. For work that
must survive your machine, create a routine with `/schedule` (runs on
Anthropic's cloud, research preview).

## Recipe: recurring audit (proactive, example — not shipped)

A routine you could create once the project is instantiated:

```
/schedule every monday 9am: run /security-scan on the repo. /goal: every
finding is triaged into an issue or dismissed with a reason, stop after 3
tries per finding.
```

For the full composition (routine + goal + parallel workflows + adversarial
review), the canonical shape is: a schedule checks for new work; a goal
defines "done" per item; workflows explore fixes in parallel worktrees; a
second agent with fresh context (`.claude/agents/code-reviewer.md`) reviews
adversarially — the author never approves its own work.

Deterministic stop conditions belong in hooks, not prompts:
`.claude/hooks/task-completed.sh` is the template's reference gate (blocks
"done" until tests/lint pass). Wire it when running Agent Teams or proactive
flows.

## Cost rules

1. Match the interval to the real change frequency of what you observe — an
   ~8-minute CI run deserves one ~8-minute check, not eight 1-minute ones.
2. Always set a cap (`stop after N tries`); always define a verifiable "done".
3. Pilot on a small slice before a large run — workflows can spawn hundreds of
   agents.
4. Route repetitive work to a smaller/faster model; reserve the capable model
   for judgment calls.
5. Prefer a script over reasoning for deterministic steps (a skill can embed
   the script).
6. Review consumption: `/usage` (per skill/subagent/MCP), `/goal` with no
   arguments (turns + tokens so far), `/workflows` (per-agent cost, stoppable).
